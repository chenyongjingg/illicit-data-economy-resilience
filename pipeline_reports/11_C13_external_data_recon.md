## 7. 更正 C-99：§2 的「实测核验」是**读错了我自己的量**

**结论先说**：§2 记的 `bytes 9,158,656` 和 `sha256 cc92f9fa…` **不是该报告的属性**，
是我**下载到的那一段**的属性。报告本身是 **31,921,548 B**。
`data/external/c13_recon/dwcon_leak_posture_2025-03.pdf` **是一个前缀，不是那份报告**。

### 7.1 两次独立读数一致，且两次都不是我的文件

```
本地（经代理 127.0.0.1:7897）HEAD   HTTP/1.1 200  Accept-Ranges: bytes  Content-Length: 31921548
pod（直连，不经代理）        HEAD   HTTP/2   200  accept-ranges: bytes  content-length: 31921548
```

服务器声明 **31,921,548 B**；我存下 **9,158,656 B** = **28.69%**。

### 7.2 它不是「不完整但仍是 PDF」，它连 PDF 都不是

在我本地那份 9,158,656 B 上逐字节检查：

```
startxref 在整个文件中出现次数 = 0
%%EOF     在整个文件中出现次数 = 0
尾部 64 B = /~Sdl\xa5fW\x18\\x0c{\xbcK…   ← 高熵流数据，不是 trailer
```

**不是「尾部缺了 `%%EOF`」，是整个文件里从来没有过。** 魔数 `%PDF-1.7` 在前 8 字节，
**任何前缀都有**——所以「magic 正确」对这个判断零信息量。

### 7.3 根因：我把「传输被杀之前到了多少」读成了「文件多大」

我的下载命令带了 `--max-time 60`。32 MB 在热点上 60 秒没下完 → **curl 被超时掐断**，
但它退出时 HTTP 状态**仍然是 200**（响应确实正确地开始了）。于是我的检查全部通过：
状态码 200、magic 正确、`type: application/pdf`、`size_download` 有值。
**那个「值」是 `size_download`——一个关于我的传输的量，不是关于对象的量。**

这与本项目已登记的 **C-96（out-param 哨兵）** 是**同一个错误的第二次出现**：
`cuDeviceGetCount` 失败时我从参数里读到的是我自己初始化进去的 `0`；
这里我从传输里读到的是我自己设的 60 秒掐出来的字节数。
**两次都是把「我这边的量」读成了「对象那边的量」。**

### 7.4 唯一抓到它的信号，是两个解析器**不一致**

| 解析器 | 对同一份前缀的反应 |
|---|---|
| PyMuPDF | **打开成功**，静默修复，抽出文字（所以我此前一直没发现） |
| pypdf | 拒绝：`EOF marker not found / Stream has ended unexpectedly` |

**宽容解析器的成功不是良构性的证据。** 值得记下：这次是**分歧**暴露了问题——
与 MIR 那次（两个仪器共享盲点、一致而无信息量）**方向相反**。
**一致可以毫无信息量；分歧则必然至少一个错。** 分歧必须停线。
